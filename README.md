#### 1. pdf분할병합 (PyQt5 데스크톱 앱)

- 분할 5가지: 페이지 선택 / 범위별 / N페이지씩 / 특정 페이지 뒤에서 / 균등 분할
- 병합: 여러 PDF를 순서 조정(드래그, 위로/아래로/삭제)해서 하나로 합치기
- 저장 전에 썸네일로 결과를 미리 보고, `수정`을 누르면 입력값이 그대로 남아 있는 상태로 돌아간다.
- 로직(`core`)과 화면(`ui`)을 나누고, 썸네일 생성과 Word 변환은 `QThread`로 처리해서 화면이 멈추지 않게 했다.
- 페이지 입력 파서는 `pytest`로 정상/경계/오류 케이스를 검증했다.
- `PyInstaller`로 `.exe` 파일까지 만들어 봤다.
- 올리지 않은 것: 실행 파일 `dist/PDF분할병합.exe`는 약 126MB라서 GitHub의 100MB 제한에 걸리고, `build/` 폴더는 다시 만들 수 있는 부산물이라 `.gitignore`로 제외했다. 아래 방법으로 직접 만들 수 있다.

**실행 파일(.exe) 만드는 법**

`pdf_tool` 폴더에서 아래를 순서대로 실행한다.

```powershell
pip install -r requirements.txt
pip install pyinstaller
python -m PyInstaller --noconfirm --clean "PDF분할병합.spec"
```

- 결과물은 `dist/PDF분할병합.exe` 하나로 나오고, 더블클릭하면 파이썬이 없는 PC에서도 실행된다. 처음 실행할 때는 압축을 푸느라 몇 초 걸린다.
- `PDF분할병합.spec`에는 창만 띄우는 설정(`console=False`), 아이콘 폴더(`resources`) 포함, `pdf2docx` 모듈 포함, 쓰지 않는 큰 라이브러리 제외가 들어 있다.
- 실행 파일 안에서는 파일 경로가 임시 폴더로 바뀌기 때문에, 아이콘 경로를 찾는 코드(`ui/styles.py`의 `icon_path`)에 `sys._MEIPASS`를 따로 처리해 두었다.
- 빌드 중 `Hidden import "sip" not found` 경고가 나와도 실행에는 문제가 없었다.

#### 3. pdf다운로드 (PDF 번역 웹 서버)

- Flask로 `/`(화면), `/upload`(PDF 업로드), `/translate/<job_id>`(번역), `/download/<job_id>`(결과 받기) 주소를 만들었다.
- PDF 텍스트를 3000자 단위로 쪼개서 OpenAI에 보내고, 번역되는 대로 화면에 이어 붙이도록 SSE(서버가 계속 데이터를 흘려 보내는 방식)를 사용했다.
- 암호가 걸린 PDF, 스캔본(텍스트 없음), 번역 실패 시 재시도 같은 예외 상황을 처리했다.
- API 키는 코드에 쓰지 않고 환경 변수 `OPENAI_API_KEY`로 읽는다.

**실습하면서 알게 된 것: 패키지 목록 정리하기 (`requirements.txt`)**

```powershell
pip list >> requirements.txt
pip freeze > requirements.txt
pip install -r requirements.txt
```

- `pip list >> requirements.txt`
  - 커서(코딩 에이전트)가 코드를 만들고 실행하려면 패키지가 설치돼 있어야 하는데, 목록이 없으면 내 컴퓨터를 돌아다니며 찾느라 시간과 토큰이 많이 든다.
  - 이 명령어로 패키지 목록을 파일로 만들어 두면 어떤 패키지가 있는지, 설치가 필요한 게 무엇인지 바로 알 수 있어서 코드를 만들기가 쉬워진다.
  - 이 파일은 **커서가 읽는 참고용**이다. 형식이 설치용이 아니라서 `pip install`로는 설치되지 않는다.
  - `>`는 파일을 덮어쓰고, `>>`는 기존 내용은 두고 뒤에 이어 붙인다.
- `pip freeze > requirements.txt`
  - 내 코드를 다른 사람에게 주려면 상대방에게도 파이썬이 있어야 하고, 내가 쓴 것과 같은 버전의 패키지가 설치돼 있어야 한다.
  - `pip freeze`는 내 PC에 설치된 패키지를 `패키지==버전` 형식으로 뽑아 준다.
- `pip install -r requirements.txt`
  - 받은 사람이 이 명령어를 실행하면 파일에 적힌 버전 그대로 한 번에 설치된다.

  - 저장소에 있는 `app.py`는 Gradio 버전이다.

  - 왼쪽은 이미지 업로드, 오른쪽은 웹캠 실시간 탐지로 화면을 나눴다.
  - 탐지된 사물마다 박스, 클래스 이름, 신뢰도(예: `person 0.91`)를 그려서 돌려준다. 신뢰도 0.25 미만은 걸러낸다.
  - 웹캠은 0.1초마다 프레임을 받아 탐지하고, 모델이 동시에 여러 번 불리지 않도록 `Lock`으로 감쌌다.
- 가중치 파일(`yolo11n.pt`)
  - 이미 학습이 끝난 모델의 값을 담은 파일이다. 코드에서 `YOLO("yolo11n.pt")`로 불러다 쓰기만 하면 되고, 직접 학습하지 않아도 사물을 찾을 수 있다.
  - 약 5MB라서 저장소에 같이 올렸다. (100MB가 넘는 모델 파일은 GitHub 용량 제한 때문에 `.gitignore`로 제외해 둔 상태다.)
- `test.ipynb`는 앱으로 만들기 전에 노트북에서 먼저 돌려 본 실험이고, `아나바다_인형.png`는 테스트에 쓴 이미지다.
- `requirements.txt`는 `pip list`로 뽑은 패키지 목록이라 커서가 읽는 참고용이다. 설치용이 아니다.

### 실습 2. 요리 추천 앱 (`작업방/요리추천앱`)

냉장고 재료를 입력하면 지금 만들 수 있는 요리를 추천해 주는 앱이다. 이번에는 바로 코드를 시키지 않고, **스킬로 아이디어를 구체화하고 기획서(PRD)를 먼저 만든 뒤** 그 문서로 코드를 만들었다.

진행 순서

1. [skills.sh](https://skills.sh)에서 `grillme`와 `to-spec` 스킬을 설치한다.
2. `/grillme`로 아이디어를 뽑는다. AI가 질문을 계속 던지면서 내 아이디어의 빈틈을 채워 준다. (이 앱은 문답 18번까지 진행했다.)
3. `/to-spec`으로 문답 결과를 PRD(`PRD.md`)로 정리한다.
4. 나온 `PRD.md`를 기준으로 코드를 작성한다.

`PRD.md`에는 해결할 문제, 해결 방법, 사용자 스토리 40개, 구현 결정, 테스트 방법, 이번에 하지 않을 것(범위 밖)이 들어 있다. 사진 인식은 범위에서 뺐고, 이 때문에 실습 1의 YOLO와는 연결되지 않는다.

앱 기능 (Gradio, 상단 메뉴로 3개 페이지 이동)

- 재료 목록: 재료명, 수량, 유통기한, 분류를 추가·수정·삭제한다. 직접 입력, 빠른 입력, 자주 쓰는 재료 선택 세 가지로 넣을 수 있다. SQLite에 저장해서 앱을 껐다 켜도 남는다. 유통기한이 D-3 이내면 "임박", 지났으면 "만료"로 표시한다.
- 추천 레시피: 가진 재료로 필수 재료가 모두 있으면 "바로 가능", 1~2개 부족하면 "조금 부족"으로 보여 준다. 임박한 재료를 쓰는 요리가 위로 올라온다. 맞는 요리가 없을 때는 "AI 레시피 생성" 버튼으로 OpenAI가 만든 "AI 추천"을 따로 받아 볼 수 있다. 저장은 하지 않고 매번 새로 만든다.
- 전체 레시피: `recipes.json`의 한식 위주 레시피 약 50개를 검색해서 본다.

구조와 테스트

- 재료 저장(`inventory_store`), 유통기한 판정(`expiry`), 재료 이름 통일(`normalize`, 달걀/계란 등), 추천 엔진(`recommender`), AI 생성(`ai_recipe`)을 `core/`에 나눠 두고 화면(`app.py`)은 불러다 쓰기만 한다.
- `tests/`에 `pytest`로 추천 엔진, 재고 저장소, 레시피 데이터, AI 응답 해석, 앱 기본 동작을 검증했다. 날짜는 고정해서 넣고, AI 호출은 테스트에서 부르지 않는다.
- OpenAI API 키는 코드에 쓰지 않고 환경 변수 `OPENAI_API_KEY`로만 읽는다. 키가 없어도 AI 추천을 뺀 나머지는 동작한다.
- 올리지 않은 것: `data/pantry.db`는 내가 입력한 재료가 담긴 개인 데이터라서 앱 폴더의 `.gitignore`로 제외했다. 처음 실행하면 새로 만들어진다.

### 실습 3. Local RAG (`작업방/local_rag`)

PDF를 올리면 그 문서 내용만 근거로 답해 주는 챗봇을 만들었다. 오전에 노트북으로 따라 한 RAG(`Ch9`)는 OpenAI API를 썼는데, 이번에는 **답변 모델과 임베딩 모델을 전부 내 PC에서 돌렸다.** API 키도 필요 없다.

- 실행: `python app.py` 후 `http://127.0.0.1:5000` 접속 (Flask). 왼쪽에서 PDF를 여러 개 올리거나 끌어다 놓고 질문하는 ChatGPT 스타일 화면이다.
- 사용한 모델
  - 답변: EXAONE-3.5-2.4B-Instruct (GGUF, Q5_K_M)
  - 임베딩: bge-m3
  - 둘 다 `llama-cpp-python`으로 실행한다. 이 라이브러리는 GGUF 형식만 읽는다.
- 처리 흐름: `PyPDFLoader`로 PDF 읽기 → `RecursiveCharacterTextSplitter`로 자르기 → bge-m3로 임베딩 → ChromaDB에 저장 → 질문과 가까운 조각을 찾아 EXAONE에게 근거로 넘기기

파일 구성

- `app.py`: Flask 서버. 업로드, 문서 목록·삭제, 스트리밍 채팅, 조각 요약, 대화 초기화 API가 있다.
- `rag.py`: 위 RAG 흐름을 모아 둔 파일.
- `config.py`: 모델 경로, 조각 크기, 검색 개수, 기준값을 한곳에 모았다.
- `templates/`, `static/`: 화면(HTML, CSS, JS).

RAG를 다듬으면서 정한 규칙

- 자르기: 500자 단위, 100자씩 겹치게 하고 문단 → 문장 순으로 끊는다. 겹치게 하는 이유는 문장이 경계에서 잘려도 앞뒤 맥락이 남게 하기 위해서다.
- 검색: 코사인 유사도가 높은 상위 4개를 쓴다. "그럼 그건 언제야?" 같은 후속 질문은 최근 질문 2개와 합쳐서도 검색한다.
- 모르면 모른다고 답하기: 가장 비슷한 조각도 유사도가 0.55보다 낮으면 모델을 부르지 않고 "정보가 없어서 답변할 수 없습니다"라고만 답한다. 이전 대화 주제에 끌려가는 엉뚱한 질문(문서 얘기 중 "프랑스 혁명은?")은 현재 질문만의 유사도가 0.4보다 낮으면 막는다. 기준값은 환경 변수로 바꿀 수 있다.
- 대화 기억: 세션별로 최근 3턴만 프롬프트에 넣고, "새 대화" 버튼으로 초기화한다.
- 출처 표시: 답변 아래에 파일명, 페이지, 유사도, 조각 요약, 원문 보기를 붙여서 근거를 확인할 수 있다.

환경에서 막혔던 것

- 설치되어 있던 `llama-cpp-python`이 CUDA 빌드여서, NVIDIA GPU가 없는 PC에서는 `llama.dll`을 못 불러왔다. 같은 버전(0.3.33)의 CPU 빌드로 다시 설치해서 해결했다.
- bge-m3는 HuggingFace(PyTorch) 형식이라 llama.cpp가 못 읽는다. llama.cpp의 `convert_hf_to_gguf.py`로 GGUF로 변환했다. 변환 전후 임베딩 유사도가 0.99999로 거의 같았다.
- CPU(i5-1135G7)만 쓰니 답변 하나에 약 40초가 걸렸다. 로컬 모델은 API보다 느리다는 걸 직접 확인했다.

올리지 않은 것

- 모델 파일(EXAONE `.gguf` 약 1.8GB, bge-m3 변환본 약 1.1GB, 원본 가중치 약 2GB)은 GitHub 100MB 제한 때문에 `.gitignore`로 제외했다. 처음 실행하려면 모델을 따로 받아서 `models/` 안에 넣어야 한다.
- `uploads/`(내가 올려 본 PDF)와 `chroma_db/`(그 PDF로 만든 벡터 DB)는 실행하면 생기는 파일이라 제외했다.
- `requirements.txt`는 `pip list` 전체를 담은 참고용 목록이다.

### 3일차 정리

- 코드를 바로 시키는 것보다, 질문으로 아이디어를 다듬고 PRD를 먼저 쓴 뒤 코드를 만드니 무엇을 만들지 기준이 문서로 남았다. PRD의 "하지 않을 것"이 범위를 지켜 주는 역할을 했다.
- 같은 사물 인식이라도 Flask와 Gradio는 서버를 띄우는 방식과 포트(5000, 7860)가 다르다. Gradio는 화면 구성까지 같이 해 줘서 짧은 코드로 업로드와 웹캠 화면을 만들 수 있었다.
- 가중치 파일은 모델이 배운 결과물이라, 작으면 같이 올리고 크면 `.gitignore`로 빼서 따로 받게 한다.
- RAG는 "찾아서 넘기기"만큼 "근거가 없으면 답하지 않기"가 중요했다. 유사도 기준값을 두면 문서에 없는 질문은 모델을 부르지 않고 바로 막을 수 있다.
- 로컬 모델은 비용과 키 걱정이 없는 대신 설치 환경(CPU/GPU 빌드, GGUF 변환)과 속도를 직접 챙겨야 한다.

### 실습 1. 계약서 검토 RAG (`작업방/계약서검토`)

가이드라인·약관 PDF를 RAG로 넣고, 검토할 계약서를 올리면 문장마다 위배 여부를 표시해 주는 Flask 웹이다. 주소는 `http://127.0.0.1:5050`이다. 5000번은 다른 예제와 겹치기 쉬워 포트를 바꿨다.

쓰는 순서

1. 왼쪽에서 **RAG 파일 업로드**로 기준 문서(약관, 가이드라인)를 넣는다.
2. **계약서 업로드**로 검토할 PDF를 넣는다.
3. **계약서 검토**를 누르면 문장마다 문제 여부와 수정 문구가 흘러나온다.
4. 아래 입력창으로는 일반 질문도 할 수 있다. 이 채팅은 RAG를 쓰지 않는다.

처리 흐름

- RAG: `PyPDFLoader` → 30자 단위로 자르기(겹침 5자) → `text-embedding-3-small` → Chroma에 저장.
- 계약서: 같은 30자로 자르되 겹침은 0이다. 잘린 조각이 검토 단위가 된다.
- 검토는 LangGraph다. `retrieve`(비슷한 약관 검색) → `review`(위배 판단·수정문) → 문제가 있을 때만 `verify`(수정이 정말 필요한지 한 번 더 확인). 불필요한 수정을 줄이려고 검증 단계를 넣었다.
- 오래 걸리는 작업은 결과를 한 번에 주지 않고, 한 줄에 JSON 하나(NDJSON)로 흘려보낸다. 그래서 진행률과 검토 결과가 화면에 바로 그려진다.

모델은 `gpt-4o-mini`, 키는 환경 변수 `OPENAI_API_KEY`만 쓴다. 올리지 않은 것: `uploads/`(잠깐 저장했다가 지우는 PDF), `chroma_db/`(그 문서로 만든 벡터 DB). 둘 다 실행하면 생긴다.

### 실습 2. 고객사 VOC 분석 Agent (`작업방/고객voc분석`)

고객 불만 CSV를 넣으면 통계, 이슈, Word 보고서까지 만들어 주는 Gradio 앱이다. 수업에서 본 CrewAI를 그대로 썼다. 실행은 `python voc_agent_app.py`.

Agent 세 개가 순서대로 돈다.

- VOC Agent: CSV를 읽고 산업군·제품·분야 막대그래프(Plotly)와 워드클라우드를 만든다.
- Issue Agent: 산업군별로 불만을 묶어 주요 이슈와 개선 과제를 뽑는다.
- Report Agent: 위 결과를 Word(`.docx`) 보고서로 저장한다.

샘플 데이터는 `sample_voc.csv`다. 열은 순번, 일자, 고객명, 산업군, 지역, 제품명, 분야, 불만이다. 모델은 기본 `gpt-4o-mini`이고 `VOC_LLM_MODEL`로 바꿀 수 있다. 올리지 않은 것: `outputs/`에 생기는 그래프, 워드클라우드, 보고서. 돌릴 때마다 새로 만들어진다.

### 실습 3. 재고관리 시스템 Agent (`작업방/재고관리시스템`)

소형 창고 재고를 화면에서 등록하고, 채팅으로도 "USB-C 케이블 10개 입고"처럼 말할 수 있는 Flask 앱이다. **SQLite가 필수**다. 화면 버튼이든 에이전트든 결국 `inventory.db`에 같은 SQL(조회 `SELECT`, 등록 `INSERT` 등)을 실행한다.

테이블

- `categories`: 분류(케이블, 공구, 소모품, 기타)
- `products`: 제품명, 최소 재고량
- `movements`: 입고·출고 내역

화면에는 제품 등록, 입출고, 재고 조회, 이력, 관리자, `/chat` 채팅이 있다. 채팅 에이전트는 LangGraph다. 먼저 규칙으로 의도를 읽고, 안 되면 LLM이 `register_product` / `stock_in` / `stock_out` / `low_stock` / `history` / `threshold` / `send_order` 중 하나로 분류한 뒤, 그에 맞는 쿼리를 실행한다. LLM에게 SQL을 직접 만들게 하지 않는다. 잘못된 쿼리가 나가지 않게 코드에서만 SQL을 짠다.

발주 메일은 `.env`의 Gmail 앱 비밀번호로 보낸다. `.env`와 실행 중 채워지는 `inventory.db`는 올리지 않았다. 서버를 켜면 `init_db()`가 테이블을 만들고, 메일 설정은 `.env.example`을 복사해 값을 넣으면 된다. `OPENAI_API_KEY`가 없어도 규칙으로 처리되는 문장은 동작한다.

### 실습 4. 뉴스 수집 분석 Agent (`작업방/뉴스수집`)

키워드를 넣으면 뉴스를 모으고, 이슈를 정리하고, Word 보고서까지 만드는 Gradio 앱이다. 실행은 `python news_agent_app.py`. LangGraph 노드는 세 개다.

- `news`: SerpAPI로 구글 뉴스 또는 네이버 뉴스를 가져온다.
- `analyze`: 비슷한 기사를 묶고, 요약·시사점, 워드클라우드, 빈도 그래프를 만든다.
- `report`: Word(`.docx`) 보고서를 만들어 받을 수 있게 한다.

키는 두 개다. SerpAPI는 `.env`의 `SERPAPI_API_KEY`, 요약은 `OPENAI_API_KEY`. `.env`는 올리지 않았고 `.env.example`만 올렸다. 분석 결과물 폴더(`outputs/`)도 실행하면 생기므로 제외했다.

### 4일차 정리

- CrewAI는 역할이 다른 Agent를 순서(또는 매니저)로 돌리는 방식이고, LangGraph는 상태와 노드, 가지치기로 한 건의 흐름을 그리는 방식이다. VOC는 전자, 계약서 검토·재고·뉴스는 후자에 가깝다.
- 계약서 검토는 "찾아서 고치기"만 하면 과하게 고친다. 검색 다음에 검증 노드를 두니 근거가 약한 수정이 줄었다.
- 재고관리는 자연어 창이 있어도 DB와 쿼리가 없으면 아무것도 안 변한다. 에이전트는 의도를 읽고, 실제 변경은 SQL이 한다.
- API 키와 메일 비밀번호는 코드가 아니라 `.env`에만 둔다. 저장소에는 예제 파일만 올렸다.

### 과제2. 영업기회 발굴 Agent (`과제수행/과제2. 영업기회 발굴 agent`)

영업 담당자가 거래처를 고르면 기본 정보, 매출, 방문일지, 뉴스를 한 화면에서 보고, 방문 준비 보고서 초안까지 받는 Streamlit 앱이다. 실행은 `streamlit run app.py`.

화면 구성

- 지도: 위경도가 있는 거래처를 핀으로 찍는다. 마우스를 올리면 요약, 클릭하면 상세가 열린다.
- 위치 없는 거래처는 따로 목록으로 빼서 같은 방식으로 고를 수 있다.
- 왼쪽에는 방문 달력과, 선택한 거래처에 대해 묻는 챗봇이 있다.
- 상세 패널에서 보고서 초안을 만들고, 고친 뒤 저장할 수 있다.

데이터는 `data/`의 Excel 네 개다. `customer_info`, `customer_meeting`, `customer_news`, `customer_sales`. 엑셀 컬럼명은 `config.py`의 `COLUMN_MAP`에서만 읽고, 코드 안에는 직접 쓰지 않았다. 파일을 폴더 루트에서 `data/`로 옮겨 두었다.

상태(신규·일반·위험) 규칙은 `config.py`에서 켠다. 지금은 임계값을 비워 두어 대부분 일반으로 나오고, 데모용으로 지정한 거래처만 신규로 보이게 했다. 매출 감소·반복 요청 규칙도 같은 파일에서 숫자를 넣으면 켜진다.

LLM 키는 `.env`의 `LLM_API_KEY`다. 키가 없어도 지도와 자료 조회는 되고, 보고서만 자료 기반으로 비어 있는 초안이 나온다. `.env`는 올리지 않았고 `.env.example`만 올렸다.
